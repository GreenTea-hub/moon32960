# 标准符合性说明（CONFORMANCE）

本文回答四个问题：目标版本是什么、覆盖到哪里、加解密由谁负责、什么条件才算「完整符合」。凡未做到的部分直接列出。

## 1. 目标版本

**主目标：GB/T 32960.3-2016**《电动汽车远程服务与管理系统技术规范 第 3 部分：通信协议及数据格式》。

2016 版是在网车辆与各级平台实际执行的事实标准，也是 2025 版切换期的存量基线。GB/T 32960.3-2025 列为第二目标（差异见第 6 节），两者报文头一致。

字段依据：国标正文（表 3 命令标识、表 4 应答标志、表 5 时间定义、表 6 车辆登入、表 7 实时信息上报、表 8 车辆登出、表 15/16 驱动电机、表 19 报警、表 20 极值、表 21/22 车辆位置）与附录 B 的通信流程（B.1 连接建立、B.2 信息传输）。

## 2. 报文结构

```
偏移  长度  字段            说明
0     2     起始符          固定 0x23 0x23
2     1     命令单元        表 3
3     1     应答标志        0x01 成功 / 0x02 失败 / 0x03 VIN 重复 / 0xFE 命令包 / 0xFF 无效
4     17    车辆识别码      VIN，ASCII
21    1     数据加密方式    0x01 不加密 / 0x02 RSA / 0x03 AES128 / 0xFE 异常 / 0xFF 无效
22    2     数据单元长度    大端 WORD，0~65531
24    N     数据单元        加密时为密文
24+N  1     校验码          BCC 异或，范围：偏移 2 至 23+N，覆盖密文
```

要点：
- WORD / DWORD 为大端（网络字节序）；
- **校验码在密文之上计算**，即先加密再校验；
- 应答标志 0xFE 是命令包标记，主动发起方必须置 0xFE；非 0xFE 的包是应答包，被动方不再应答。

## 3. 应答语义（按附录 B 统一）

| 上行命令 | 校验正确 | 校验失败 |
|---|---|---|
| 0x01 车辆登入 | 应答 0x01 成功 | 忽略所接收数据，**不应答** |
| 0x01 且 VIN 已在线 | 应答 0x03 VIN 重复 | — |
| 0x02 实时信息上报 | **不做应答** | 应答 0x02，终端间隔 1min 重发至多 3 次 |
| 0x03 补发信息上报 | **不做应答** | 应答 0x02 |
| 0x04 车辆登出 | 应答 0x01 | 应答 0x02 |
| 0x07 心跳 | 应答 0x01 | — |
| 0x08 终端校时 | 应答 0x01 | — |
| 其他命令 | 应答 0x02 | — |

终端侧配套行为（本项目文档化，不在库内实现）：
- 登入后 3 分钟内未收到应答应重发；连续 3 次无应答应间隔 30 分钟重连，并把链路恢复前存储的数据补发；
- 实时上报校验失败时按 1 分钟间隔重发，失败 3 次后停止。

应答包构造：命令单元与请求相同，应答标志改结果，**删除其余报文内容**，加密方式回到 0x01，重新计算 BCC。默认数据单元为空；`response_frame_with_time` 提供携带 6 字节应答时间的变体，供要求保留时间的地方口径使用。

## 4. 加解密接入责任

GB/T 32960.3-2016 只定义「数据加密方式」字节的取值，**不定义密钥协商、密钥管理与分组填充**；通信安全要求由 GB/T 40855 规定，密钥由部署方持有。因此本项目把责任划成三段：

| 环节 | 责任方 | 本项目提供 |
|---|---|---|
| 密文承载、加密方式字段、校验覆盖顺序 | 本项目 | 帧层按 0x01/0x02/0x03 处理，先加密再算 BCC |
| AES128 加解密 | 本项目内置 | 纯 MoonBit AES-128，ECB 与 CBC 两种模式，FIPS-197 向量验证；默认 PKCS#7 填充 |
| 密钥生成、分发、轮换 | 部署方 | 通过 `KeyMaterial` 显式注入，不做隐式约定 |
| RSA 私钥持有与解密 | 部署方 | `KeyMaterial` 无 RSA 实现时抛 `CryptoUnavailable`，拒绝该帧并应答 0x02，**绝不当明文解析** |
| 填充与分组模式约定 | 部署方 + 本项目默认 | 标准未规定，默认 ECB + PKCS#7；CBC 需显式给 IV，可由部署方替换 |

这样「任一 2016 版合规终端」的三种加密形态都有确定处置：明文直解、AES128 注入密钥后解、RSA 注入私钥后解；未注入密钥时按拒绝语义处理，而不是假装能解。

## 5. 兼容性终点（统一口径）

满足以下七条，视为对本标准完整符合：

1. **明文入站**：任一 2016 版合规终端的 0x01/0x02/0x03/0x04/0x07 帧，逐字段可解；
2. **加密入站**：0x03 AES128 帧在注入密钥后逐字段可解（本仓库内置实现，含 48 字节密文用例）；0x02 RSA 帧在部署方注入私钥解密实现后走同一解析路径；
3. **出站应答**：应答语义严格按第 3 节，实时与补发在正确时不应答，登入必须应答；
4. **拒绝语义**：长度不符、校验码错误、VIN 非法、未知信息类型、计数越界、解密失败，均给出可定位错误；报头可读时回 0x02，报头不可读则不应答；
5. **会话状态**：登入 → 在线 → 上报/心跳/补发 → 登出 → 关闭，顺序错误拒绝；
6. **补发窗口**：补发按 7 日窗口校验，超窗拒绝；
7. **九类信息体**：整车、驱动电机、燃料电池、发动机、车辆位置、极值、报警、储能电压、储能温度全部可解析与再编码。

不在此终点：TCP 传输层、GB/T 40855 规定的密钥管理体系、2025 版新增字段集。

## 6. 与 2025 版的主要差异

| 变化 | 本项目处理 |
|---|---|
| 新增信息类型（蓄电池最小并联单元电压、蓄电池温度、燃料电池电堆、超级电容器及其极值） | 未实现，标志位抛 `UnsupportedInfoType` |
| 删除 2016 版动力蓄电池极值数据（0x06） | 仍按 2016 解析，兼容存量 |
| 驱动电机删除控制器输入电压与母线电流（12 → 9 字节） | 按 2016 的 12 字节解析；2025 报文会错位，列为待做 |
| 登入删除储能子系统数/编码，改为 BMS 个数与蓄电池包编码 | 登入仍按 2016，2025 需分支 |
| 整车数据取值范围调整、位置明确 GCJ-02、报警等级增至 0~4 | 码值不变，仅校验范围与文档说明差异 |

## 7. 覆盖矩阵

### 7.1 命令单元

| 命令 | 解析 | 应答 | 加密 |
|---|---|---|---|
| 0x01 车辆登入 | ✅ 表 6 | ✅ 0x01 / 0x03 | ✅ |
| 0x02 实时上报 | ✅ 九类信息体 | ✅ 正确时不应答 | ✅ |
| 0x03 补发上报 | ✅ 同 0x02 | ✅ 正确时不应答 | ✅ |
| 0x04 车辆登出 | ✅ 表 8 | ✅ 0x01 | ✅ |
| 0x05 平台登入 | ✅ 表 9（41 字节） | — | ✅ |
| 0x06 平台登出 | ⚠️ 按登出格式 | — | ✅ |
| 0x07 心跳 | ✅ 空数据单元 | ✅ 0x01 | ✅ |
| 0x08 终端校时 | ⚠️ 仅应答 | ✅ 0x01 | ✅ |
| 0x80 平台下行 | ⚠️ 原始负载 | — | ✅ |

### 7.2 信息类型

| 标志 | 类型 | 长度 | 状态 |
|---|---|---|---|
| 0x01 | 整车数据 | 20 | ✅ 13 字段含换算 |
| 0x02 | 驱动电机 | 1 + 12n | ✅ |
| 0x03 | 燃料电池 | 18 + N | ✅ 探针变长 |
| 0x04 | 发动机 | 5 | ✅ |
| 0x05 | 车辆位置 | 9 | ✅ 状态位解析 |
| 0x06 | 极值数据 | 14 | ✅ |
| 0x07 | 报警数据 | 10 + Σ | ✅ 五组故障列表 |
| 0x08 | 储能电压 | 1 + Σ | ✅ |
| 0x09 | 储能温度 | 7 + Σ | ✅ |

异常与无效码按 BYTE 0xFE/0xFF、WORD 0xFFFE/0xFFFF、DWORD 0xFFFFFFFE/0xFFFFFFFF 分级保留，换算函数返回 `None`。

## 8. 未覆盖项

| 项 | 现状 | 影响 |
|---|---|---|
| RSA 解密 | 未内置大数运算与 PKCS#1 解填充，需部署方注入 | 0x02 帧只能拒绝，不能解 |
| TCP 传输层 | 未实现监听、粘包拆包、连接管理 | 以帧为单位，由调用方喂数据 |
| 平台登出 0x06 | 按 8 字节登出格式解析 | 平台间通信场景不完整 |
| 终端校时 0x08 | 只应答，未解析校时时间 | 校时链路未闭环 |
| 平台下行 0x80 | 保留原始负载 | 下行命令需上层解码 |
| 2025 版数据单元 | 未新增分支 | 见第 6 节 |
| 分组填充约定 | 默认 PKCS#7 | 与部分厂商约定可能不同，需按现场替换 |

## 9. 验证方式

- `moon test`：51 条用例，覆盖 AES-128 FIPS-197 向量、明文与密文黄金帧、应答语义（登入应答 / 实时不应答 / VIN 重复 / 校验失败回 0x02）、九类信息体、状态机与补发窗口；
- `moon run cmd/main -- case login|encrypted|report|resend`：四个端到端案例；
- 黄金帧与密钥固定为常量，任何布局或语义改动都会让测试失败。

## 10. 与标准正文的差异申报

四处依据公开解读，需与正文最终核对，当前行为已由测试固定：

1. 实时上报在采集时间后是否还有 2 字节信息流水号（两种布局都支持，默认不带）；
2. 整车数据是否含加速踏板行程值与制动踏板状态（按 13 字段 20 字节）；
3. 燃料电池氢系统子项长度（按 18 + N）；
4. 应答包是否保留 6 字节应答时间（默认空，另有 `response_frame_with_time`）。
