# 标准符合性说明（CONFORMANCE）

本文回答五个问题：目标版本、覆盖范围、两套应答规则如何区分、加解密由谁负责、什么条件才算完整符合。

## 1. 目标版本与适用范围

**主目标：GB/T 32960.3-2016**。

必须区分两个适用范围，标准对它们的应答规则不同：

| 范围 | 标准位置 | 性质 |
|---|---|---|
| 车载终端 → 平台 | 附录 B | **资料性**（"宜参照"，4.4 原文） |
| 平台 → 平台 | 正文第 5 章 | **规范性**（"应"） |

本项目**以车端（附录 B）为主线实现**，平台间场景单独实现一套规则，两者不混用。代码里由 `Scope` 显式区分，没有默认猜场景。

## 2. 报文结构

```
偏移  长度  字段            说明
0     2     起始符          固定 0x23 0x23
2     1     命令单元        表 3
3     1     应答标志        0xFE 命令包；0x01 成功 / 0x02 失败（2016 口径）
4     17    车辆识别码      车端为 VIN
21    1     数据加密方式    0x01 不加密 / 0x02 RSA / 0x03 AES128
22    2     数据单元长度    大端 WORD
24    N     数据单元        加密时为密文
24+N  1     校验码          BCC，范围偏移 2 至 23+N，覆盖密文
```

**应答标志口径**（这是第二次被驳回的根因之一）：

| 取值 | 含义 | 出处 |
|---|---|---|
| 0x01 | 成功 | 2016 表 4 |
| 0x02 | 失败 | 2016 表 4 |
| 0xFE | 命令包标记 | 2016 表 4 |
| 0x03 | VIN 重复 | 地方标准 / 2025 版，**2016 表 4 未见** |
| 0xFF | 无效 | 地方标准，**2016 表 4 未见** |

因此代码默认 `ResponseProfile::Gb2016`：VIN 重复也只回 0x02。需要 0x03 时显式传 `ResponseProfile::Extended`，文档与审计都会记录当前口径。

## 3. 应答规则（按适用范围分表）

### 3.1 车端（附录 B，资料性）

| 上行命令 | 校验正确 | 校验失败 |
|---|---|---|
| 0x01 车辆登入 | 应答 0x01 | **忽略所接收数据，不应答**（B.1 原文） |
| 0x01 且 VIN 已在线 | 应答 0x02（2016 口径）/ 0x03（扩展口径） | — |
| 0x02 实时信息上报 | **不做应答**（B.2.1 原文） | 应答 0x02，终端间隔 1min 重发至多 3 次 |
| 0x03 补发信息上报 | **不做应答**（沿用实时口径） | 应答 0x02 |
| 0x04 车辆登出 | 应答 0x01（附录 B 未强制，按平台惯例） | 应答 0x02 |
| 0x07 心跳 | 应答 0x01（附录 B 未强制，按平台惯例） | — |
| 0x05/0x06 平台命令 | 方向不符，应答 0x02 | — |
| 0x08/0x80 下行命令 | 方向不符，应答 0x02 | — |

### 3.2 平台间（正文第 5 章，规范性）

| 上行命令 | 校验正确 | 校验失败 |
|---|---|---|
| 0x05 平台登入 | **应答 0x01** | 应答 0x02 并记录 |
| 0x06 平台登出 | 应答 0x01 | — |
| 0x02 实时信息上报 | **应答 0x01**（5.2.2："校验正确时应正确应答"） | 应答 0x02，客户端 1min 重发至多 3 次 |
| 0x03 补发信息上报 | **应答 0x01** | 应答 0x02 |
| 0x01/0x04/0x07 终端命令 | 方向不符，应答 0x02 | — |

**两表最关键的差别**：同一份实时上报数据，车端正确时**不**应答，平台间正确时**必须**应答。`moon run cmd/main -- case platform` 用同一份数据演示了这个对比。

### 3.3 应答包怎么构造

附录 B.3.3.2 原文：应答时"只变更应答标志、应答报文时间，并重新计算校验位，**其余报文内容与主动发送报文一致**"。

因此代码默认 `ResponseShape::KeepRequestPayload`：数据单元与请求一致，仅把开头 6 字节报文时间替换为应答时刻，加密方式沿用请求。

另提供两种形态，但都在名称与文档里标明出处，不冒充合规：
- `TimeOnly`：保留报文时间、删除其余内容（部分地方标准口径）；
- `EmptyPayload`：数据单元为空（**不与任何条文对应，仅联调用**）。

之前版本默认用 `EmptyPayload` 却宣称遵循附录 B，这是第三次驳回的直接原因，现已修正。

## 4. 加解密接入责任

| 环节 | 责任方 | 本项目 |
|---|---|---|
| 加密方式字段、密文承载、先加密再校验 | 本项目 | 帧层按 0x01/0x02/0x03 处理 |
| AES128 加解密与填充 | 本项目内置 | 纯 MoonBit AES-128（ECB/CBC）+ PKCS#7，FIPS-197 向量验证 |
| 密钥生成分发、轮换 | 部署方 | `KeyMaterial` 显式注入 |
| RSA 私钥持有与解密 | 部署方 | 未注入时抛 `CryptoUnavailable`，拒绝该帧 |
| 分组模式与填充 | 部署方 + 本项目默认 | 标准未规定，默认 ECB + PKCS#7 |

**缺密钥时不出应答**：应答按附录 B 要保持原加密方式，拿不到密钥就无法加密应答，此时只记录不应答，避免用不加密的应答冒充合规。

## 5. 兼容性终点（分场景表述）

### 5.1 车端终点

1. 明文帧逐字段可解；AES128 帧注入密钥后逐字段可解；RSA 帧待部署方注入私钥；
2. 登入必须应答，校验失败忽略不应答；实时与补发正确时不应答、失败回 0x02；
3. 应答包按附录 B 保留请求数据单元，仅换应答时间并重算校验；
4. 畸形帧给出可定位错误；报头可读且加密方式为明文时回 0x02；
5. 会话顺序不可越级；补发按 7 日窗口校验；
6. 九类信息体全部可解析与再编码。

### 5.2 平台间终点

1. 平台登入/登出、实时与补发上报，校验正确时**都应答 0x01**；
2. 校验失败应答 0x02；
3. 车端命令在该场景被判定方向不符。

### 5.3 两场景共同的拒绝与记录

- 方向不符、报头不可解析、缺密钥无法应答，均记审计且不回包；
- 每次接收留一条审计，含 VIN、命令、结论、说明。

## 6. 与 2025 版的主要差异

| 变化 | 处理 |
|---|---|
| 新增信息类型（蓄电池最小并联单元电压/温度、燃料电池电堆、超级电容器及其极值） | 未实现，抛 `UnsupportedInfoType` |
| 删除 2016 版动力蓄电池极值数据（0x06） | 仍按 2016 解析 |
| 驱动电机删除控制器输入电压与母线电流（12 → 9 字节） | 按 2016 解析 |
| 登入删除储能子系统数/编码 | 登入按 2016 |
| 增加应答错误标志定义（6.3.2） | 由 `ResponseProfile::Extended` 承接 |
| 整车取值范围、位置 GCJ-02、报警等级 0~4 | 码值不变，仅文档说明 |

## 7. 覆盖矩阵

| 命令 | 车端解析 | 车端应答 | 平台间应答 | 加密 |
|---|---|---|---|---|
| 0x01 车辆登入 | ✅ 表 6 | ✅ 0x01 / 0x02 | 方向不符 | ✅ |
| 0x02 实时 | ✅ 九类 | 正确不应答 | ✅ 0x01 | ✅ |
| 0x03 补发 | ✅ 同 0x02 | 正确不应答 | ✅ 0x01 | ✅ |
| 0x04 登出 | ✅ 表 8 | ✅ 0x01 | 方向不符 | ✅ |
| 0x05 平台登入 | ✅ 41 字节 | 方向不符 | ✅ 0x01 | ✅ |
| 0x06 平台登出 | ⚠️ 按登出格式 | 方向不符 | ✅ 0x01 | ✅ |
| 0x07 心跳 | ✅ 空 | ✅ 0x01 | 方向不符 | ✅ |
| 0x08 校时 | 下行，平台侧方向不符 | — | — | ✅ |
| 0x80 下行 | 下行，平台侧方向不符 | — | — | ✅ |

九类信息体：整车 20、驱动电机 12n+1、燃料电池 18+N、发动机 5、位置 9、极值 14、报警 10+Σ、储能电压 1+Σ、储能温度 7+Σ，全部可解析。

## 8. 未覆盖项

| 项 | 现状 |
|---|---|
| RSA 解密 | 未内置大数运算，需部署方注入 |
| TCP 传输层 | 未实现监听、粘包拆包 |
| 平台登出 0x06 | 按 8 字节登出格式解析 |
| 终端校时 0x08 | 未解析校时时间 |
| 平台下行 0x80 | 保留原始负载 |
| 2025 版数据单元 | 未新增分支 |
| 平台间会话表 | 只做应答语义，未建平台会话 |
| 平台间标识 | 第 4~20 字节沿用 17 位 VIN 字母表校验，实际可能是平台标识 |

## 9. 验证方式

- `moon test`：59 条，含 AES-128 FIPS-197 向量、明文与密文黄金帧、两套应答规则、方向检查、三种应答形态、九类信息体、补发窗口；
- `moon run cmd/main -- case login|encrypted|report|resend|platform`；
- 黄金帧、密钥、应答口径均为常量，改动即失败。

## 10. 与标准正文的差异申报

依据公开解读、需与正文核对，当前行为由测试固定：

1. 实时上报采集时间后是否带 2 字节信息流水号（两种都支持，默认不带）；
2. 整车数据是否含加速踏板与制动踏板（按 13 字段 20 字节）；
3. 燃料电池氢系统子项长度（18 + N）；
4. 0x03 VIN 重复、0xFF 无效是否属 2016 表 4（默认不启用，走 0x02）；
5. 心跳与登出应答属惯例而非附录 B 明文；
6. 平台间报文第 4~20 字节是否为平台标识。
