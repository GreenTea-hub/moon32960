# 三个标准案例：报文 → 字段 → 应答 → 后续动作

每个案例都可以用一行命令原样复现：

```bash
moon run cmd/main -- case login
moon run cmd/main -- case report
moon run cmd/main -- case resend
```

下面的报文由本仓库的编码器生成，可直接拿去与真实终端对照。

---

## 案例一：车辆登入（命令单元 0x01）

### 报文

```
232301014c47574546344135364d463132333435360100251a0b12091e000001383938363036323031383030303132333435363701074241542d4130312a
```

### 逐字节拆解

| 偏移 | 字节 | 字段 | 取值 |
|---|---|---|---|
| 0 | `23 23` | 起始符 | `##` |
| 2 | `01` | 命令单元 | 车辆登入 |
| 3 | `01` | 应答标志 | 成功 |
| 4 | `4c47 5745 4646 3441 3536 4d46 3132 3334 3536` | 车辆识别码 | `LGWEF4A56MF123456` |
| 21 | `01` | 数据加密方式 | 不加密 |
| 22 | `00 25` | 数据单元长度 | 37 字节（大端） |
| 24 | `1a 0b 12 09 1e 00` | 登入时间 | 2026-11-18 09:30:00 |
| 30 | `00 01` | 登入流水号 | 1 |
| 32 | `3839 3836 3036 3230 3138 3030 3031 3233 3435 3637` | ICCID | `89860620180001234567` |
| 52 | `01` | 可充电储能子系统数 | 1 |
| 53 | `07` | 可充电储能系统编码长度 | 7 字节 |
| 54 | `4241 542d 4130 31` | 可充电储能系统编码 | `BAT-A01` |
| 61 | `2a` | 校验码 | BCC(偏移 2 → 60) |

数据单元 37 字节 = 6 + 2 + 20 + 1 + 1 + 7，与长度字段一致。

### 字段

```
登入时间    : 2026-11-18 09:30:00
登入流水号  : 1
ICCID       : 89860620180001234567
储能子系统  : 1 个
编码长度    : 7 字节
子系统编码  : BAT-A01
```

ICCID 由终端从 SIM 卡读取，是身份核对的辅助条件；子系统数与编码长度决定了后面 `n×m` 字节的长度，因此这两项必须先行解析。

### 应答

```
232301014c47574546344135364d4631323334353601000024
```

命令单元与请求一致（0x01），应答标志 `01` 成功，数据单元长度 `0000`，校验码 `24`。

```
平台结论    : login-accepted（若该 VIN 已在线则为 login-duplicate，应答标志 03）
说明        : 新建会话，ICCID 共 20 位
```

### 后续动作

1. 会话状态置为在线，登记登入流水号 1；
2. 保存 ICCID 与子系统编码，供后续身份核对；
3. 该 VIN 的实时上报、补发、心跳、登出开始被接收，未登入的同类帧一律应答 `02` 失败；
4. 平台在线终端数变为 1。

## 案例二：实时信息上报（命令单元 0x02）

### 报文

```
232302014c47574546344135364d463132333435360100251a0b12091f0001010201026f0001e2400e1075944e010404b01e01050006f013c80260f688f1
```

### 逐字节拆解（数据单元 37 字节）

| 偏移 | 字节 | 字段 | 取值 |
|---|---|---|---|
| 24 | `1a 0b 12 09 1f 00` | 数据采集时间 | 2026-11-18 09:31:00 |
| 30 | `01` | 信息类型标志 | 整车数据 |
| 31 | `01` | 车辆状态 | 启动状态 |
| 32 | `02` | 充电状态 | 行驶充电 |
| 33 | `01` | 运行模式 | 纯电 |
| 34 | `02 6f` | 车速 | 623 → 62.3 km/h |
| 36 | `00 01 e2 40` | 累计里程 | 123456 → 12345.6 km |
| 40 | `0e 10` | 总电压 | 3600 → 360.0 V |
| 42 | `75 94` | 总电流 | 30100 → 10.0 A（偏移 −3000 A ×10） |
| 44 | `4e` | SOC | 78% |
| 45 | `01` | DC-DC 状态 | 工作 |
| 46 | `04` | 档位 | 4 档 |
| 47 | `04 b0` | 绝缘电阻 | 1200 → 1200 kΩ |
| 49 | `1e` | 加速踏板行程值 | 30% |
| 50 | `01` | 制动踏板状态 | 1 |
| 51 | `05` | 信息类型标志 | 车辆位置 |
| 52 | `00` | 定位状态 | 有效定位、北纬、东经 |

| 57 | `02 60 f6 88` | 纬度 | 39909000 → 39.909000 |
| 61 | `f1` | 校验码 | BCC(偏移 2 → 60) |

整车数据固定 20 字节，位置固定 9 字节，两段各带一个类型标志，合计 6 + 1 + 20 + 1 + 9 = 37。

### 字段

```
数据采集时间: 2026-11-18 09:31:00
· 整车数据 0x01
    车辆状态   车辆启动状态
    充电状态   行驶充电
    SOC        78%
    车速       62.3 km/h
    累计里程   12345.6 km
    总电压     360.0 V
    总电流     10.0 A
· 车辆位置 0x05
    定位有效   true
    经度       116.397000 东经为正
    纬度       39.909000 北纬为正
```

若任一字段为 `0xFFFE`/`0xFFFF`，对应换算返回「异常」或「无效」，不做算术。

### 应答

```
232302014c47574546344135364d4631323334353601000027
```

命令单元 0x02，应答标志 `01`，数据单元空，校验码 `27`。

### 后续动作

1. 实时计数加一，最近上报时间更新为 09:31:00；
2. 整车与位置两类信息体分别入库；
3. 通用报警标志未置位，不触发「故障前 30 秒补发」要求。

## 案例三：断线补发（命令单元 0x03）

### 场景

1. 09:30 登入并进入在线状态；
2. 09:31 链路正常，实时上报一帧被接收；
3. 09:32 至 09:35 链路中断，终端把这三帧写入本地存储；
4. 链路恢复，终端在实时上报的空闲时间补发缓存帧。

### 报文

补发 09:32：

```
232303014c47574546344135364d463132333435360100251a0b1209200001010201026f0001e2400e1075944e010404b01e01050006f013c80260f688cf
```

补发 09:33：

```
232303014c47574546344135364d463132333435360100251a0b1209210001010201026f0001e2400e1075944e010404b01e01050006f013c80260f688ce
```

与案例二逐字节比对，只有两处不同：

| 字段 | 实时帧 | 补发帧 |
|---|---|---|
| 命令单元（偏移 2） | `02` | `03` |
| 数据采集时间（偏移 24~29） | `1f`（09:31） | `20`/`21`（09:32/09:33） |
| 校验码 | 随时变化 | 随时变化 |

**数据单元格式完全相同**，这是补发能被同一套解码器处理的原因。

### 应答

每个补发帧单独应答，命令单元 `03`，应答标志 `01`。

### 后续动作

1. 补发帧计入补发计数，不污染实时计数；
2. 平台对 7 日外的补发应答 `02` 失败（`RESEND_WINDOW_SECONDS = 7 × 24 × 3600`）；
3. 会话最终状态：实时帧 1、补发帧 2、最近上报 09:33:00；
4. 若补发帧落后于最近上报超过 7 日，`TerminalSession::report(resend=true)` 抛错，网关换算为应答标志 `02`，终端据此丢弃该条缓存。

### 为什么必须区分 0x02 与 0x03

监管平台按命令单元区分「实时数据」与「补发数据」，两者的入库时间窗口、完整率统计与断链分析口径不同。若终端把缓存的旧数据用 0x02 上报，会被算作实时数据，导致时序数据出现回退；若平台把 0x03 当 0x02 处理，补发率统计失真。
